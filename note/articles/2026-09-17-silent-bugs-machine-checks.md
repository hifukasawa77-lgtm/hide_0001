AIにコードを書かせていて、一番時間を吸われるのは**バグではありません。**

**「例外もエラーも出ないのに、結果だけが間違っている状態」**です。

コンソールは綺麗です。テストは通ります。「起動して例外0件」も通ります。
それなのに、絵が1マスずれている。武将の顔が別人になっている。
音が出ていない。拠点が海の上に立っている。

私はこれを**無言で壊れるバグ**と呼んでいます。
ブラウザゲームを37本<!--fact:games-->作る過程で、これを何度も踏みました。
そのたびに数時間から数日を溶かし、しかも**同じ種類のバグを何度も繰り返しました。**

## なぜAIに書かせると、これが増えるのか

人間が書いたコードにも同じバグは出ます。ただ、AIに書かせると**頻度が上がります。**
理由は3つあると思っています。

**1. AIは「それらしいコード」を書くのが上手い。**
`ctx.drawImage(img, 900, 300, 128, 128, x, y, 64, 64)` は、どこも間違っていないように見えます。
実際、画像が1254pxのときは正しい。画像を256pxに差し替えた瞬間に壊れます。
**コードは変わっていないのに壊れる**ので、差分レビューでは絶対に見つかりません。

**2. AIは失敗を握りつぶすコードも上手い。**
`try/catch` でループを継続させる、フォールバック描画を用意する。
どちらも良い実装です。**そして、どちらも「壊れていること」を隠します。**

**3. 変更の速度が上がるぶん、副作用の確認が追いつかない。**
1セッションで20ファイル触れます。人間のレビューは、その速度に追いつきません。

つまり、**AIに書かせる開発では、目視レビューが構造的に機能しなくなります。**
だから私は、踏んだバグを1つ潰すたびに、
**「同じことが起きたら落ちる検査」を必ず1本書く**というルールにしました。
いま検査スクリプトは22本<!--fact:verifiers-->あります。

## この記事の中身

ここから先で、実際に踏んだ6種類の無言バグを、
**「どう壊れたか」「なぜ既存の検査を素通りしたか」「どんな検査を書いて止めたか」**の
3点セットで出します。検査スクリプトの実際のコードも載せます。

1. 切り出し矩形の直書き — アセットを縮めた瞬間に絵が消える
2. 配列への途中挿入 — 全員の顔が1つずつずれる
3. 例外を捕捉するループ — `pageerror` を見る検査が全部素通りする
4. Web Audio の無音 — ノードを繋ぎ忘れても例外は出ない
5. 座標の焼き込み忘れ — **自分のPCだけ正しく見える**
6. 名前による突き合わせ — 改称した日に、静かに対応が切れる

最後に、**「検査が本当に効いているかを確かめる方法」**（故障注入）を書きます。
私はこれをやって、**自分が書いた検査が素通りしていた**ことを3回見つけています。

## 1. 切り出し矩形の直書き — アセットを縮めた瞬間に絵が消える

**何が起きたか。** リポジトリが1.6GBに膨らんで GitHub Pages の1GB上限を超えたので、
画像を WebP へ再エンコードして264MBまで落としました。
その日から、戦国シミュレーションのマップ上のマーカー4種が消えました。

**なぜ素通りしたか。** 画像の読み込みは**成功しています。**404も出ません。
`drawImage` に渡した切り出し矩形が画像の外を指しているだけで、
**範囲外の drawImage は例外を投げず、何も描かずに正常終了します。**

```js
// 1254px の原寸を前提に書かれていた
ctx.drawImage(img, 900, 300, 128, 128, x, y, 64, 64);
```

原寸1254pxを256pxに縮めたので、`900, 300` はもう画像の中にありません。
実測したところ、マーカー4種の塗り面積が0〜3.5%になっていました。

**どう止めたか。** 2段構えにしました。

まず実装側。**切り出し矩形は「測ったときの原寸」と対で持ち、描画時に実解像度へ換算する**。

```js
// 矩形は「測った原寸」とセットで持つ
const SRC = { base: 1254, x: 900, y: 300, w: 128, h: 128 };
function scaleSrcRect(img, r) {
  const k = img.naturalWidth / r.base;      // 実解像度 ÷ 測ったときの原寸
  return [r.x * k, r.y * k, r.w * k, r.h * k];
}
ctx.drawImage(img, ...scaleSrcRect(img, SRC), x, y, 64, 64);
```

次に検査側。**塗り面積を実測する**検査を書きました（`scripts/verify-map-assets.mjs`）。
やっていることは単純で、

1. Playwright でページを開き、マーカーだけを空の Canvas に描かせる
2. `getImageData` で不透明ピクセルを数える
3. **塗り面積が閾値未満なら落とす**

「描画関数が呼ばれたか」ではなく「**絵が出たか**」を見るのが要点です。
呼ばれたかどうかは、このバグでは常に真になります。

さらに横断検査として、**9引数の `drawImage` で切り出し矩形が数値リテラル直書きになっている箇所**を
全ゲームHTMLから洗い出す検査も足しました（`scripts/verify-known-bug-patterns.mjs`）。
こちらは警告どまりにしてあります。**新しいゲームで同じ書き方をした瞬間に気づける**のが目的です。

## 2. 配列への途中挿入 — 全員の顔が1つずつずれる

**何が起きたか。** 武将の肖像は、1枚の大きな画像（アトラス）に格子状に並べてあります。
どの武将がどの枠を使うかは、**武将データ配列のindexで連番に配っていました。**

```js
DATA.generals.forEach((g, i) => { slots[g.id] = atlasCell(i); });
```

ある日、抜けていた武将を配列の**真ん中に**追加しました。
その瞬間、**それ以降の武将全員の顔が1つずつずれました。**

**なぜ素通りしたか。** 例外は出ません。全員に顔が付いています。
存在しない枠を指すわけでもないので、404も出ません。
**「別人の顔が出ている」ことは、その人物の顔を知らないと分からない。**
機械にとっては完全に正常な状態です。

**どう止めたか。** これは検査の書き方が難しい類です。
「正しい顔」を機械が知らないので、結果からは判定できません。

そこで、**不変条件の方を検査しました。**
index依存の配列は「**末尾追加のみ**」が守るべき性質です。だったら、

1. index割り当てに使っている配列を**登録簿に列挙しておく**
2. 比較対象（既定はHEAD）時点の並びを取り出す
3. **現在の並びの先頭一致（prefix）になっているか**を確かめる

先頭一致が崩れていれば、途中挿入か並べ替えが起きたということです。
`scripts/verify-known-bug-patterns.mjs` の検査Aがこれをやっています。

**この検査には弱点があります。登録簿に足し忘れると、静かにすり抜けます。**
なので CLAUDE.md 側に「新しいゲームで肖像アトラス等のindex依存割り当てを足したら、
この登録簿に追加すること」と明記しました。それでも忘れる可能性は残ります。
**完全ではない検査でも、無いよりはるかにマシ**という割り切りです。

なお、1枚1人の専用画像を使う武将は、`{cols:1, rows:1}` の専用スロットを作って、
**一括割り当ての後に上書きする**必要があります。順番を逆にすると一括側に潰されます。
これも例外は出ません。

## 3. 例外を捕捉するループ — `pageerror` を見る検査が全部素通りする

**何が起きたか。** 戦国シミュレーションの起動が壊れて、
「背景画像だけ残ってUIが何も出ない」状態になりました。
原因は描画関数の中の `preview is not defined` という単純な参照エラーです。

**なぜ素通りしたか。** ここが本題です。
自作エンジンのゲームループは、`update` / `draw` の例外を **`try/catch` で捕捉して継続し、
`engine.errors` に積む**設計になっていました。**良かれと思って書いた実装です。**

その結果、Playwright の `page.on('pageerror')` には**何も飛んできません。**
「起動して例外0件」の検査は、堂々と合格します。

しかも**タイトル画面は正常に出ます。**壊れているのはマップ画面の描画だからです。
私は「タイトルが出た＝起動成功」と判断し、原因を
「アセット読み込みが重いのでは」「`roundRect` が未対応なのでは」と誤診して、
**3コミット分の時間を無駄にしました。**

**どう止めたか。** 検査を2箇所直しました。

```js
// ① pageerror だけでなく、エンジンが握り潰した例外も必ず合算する
const engineErrors = await page.evaluate(() => window.engine?.errors ?? []);
const allErrors = [...pageErrors, ...engineErrors];

// ② タイトルで終わらず、実際にマップ画面まで進める
await page.click('#btn-start');
await page.waitForFunction(() => window.game?.scene === 'map');
```

そして CLAUDE.md に一般則として書きました。

> **タイトル画面が出た＝起動成功ではない。**
> 描画ループの例外は「背景画像だけ残してUIが出ない」形で現れ、タイトルは無事に出る。

**教訓は「エラーを握り潰す実装を書いたら、握り潰した先を見る検査を同時に書く」**です。
握り潰す実装自体は正しい（1フレームの失敗でゲームを落としたくない）。
問題は、握り潰したことを誰にも伝えていなかったことです。

## 4. Web Audio の無音 — ノードを繋ぎ忘れても例外は出ない

**何が起きたか。** シンセサイザーのページで、特定の操作をすると音が出なくなりました。

**なぜ素通りしたか。** Web Audio は、
**ノードを接続し忘れても、エンベロープの時刻指定を間違えても、例外を出しません。**
`AudioContext` は正常、ノードも正常、`start()` も成功。ただ無音です。

**どう止めたか。** 「例外0件」を合格条件にするのをやめて、
**`analyser.getByteFrequencyData` のピーク値まで見る**ようにしました
（`scripts/verify-synth-eq.mjs`、45項目）。音が出ているかは、音を測るしかありません。

このとき副産物で3つの罠を踏んだので、あわせて書いておきます。

**罠1: ヘッドレスでは `--autoplay-policy=no-user-gesture-required` が要る。**
無いと `AudioContext` が `suspended` のままで**全項目が無音になり**、
原因を実装側だと誤診します。私は一度これで実装を疑いました。

**罠2: `setTargetAtTime` の直後に `AudioParam.value` を読むと、まだ目標値に達していない。**
時定数の10倍ほど待ってから読まないと、
**「フェーダーがフィルターに届いていない」という偽の不合格**が出ます。
偽の不合格は、本物の不合格より有害です。**検査が信用されなくなるからです。**

**罠3: 無音判定はリバーブのIR長より長く待つ。**
2.4秒の残響があるのに600msで測ると、必ず余韻を拾って落ちます。

## 5. 座標の焼き込み忘れ — 自分のPCだけ正しく見える

**何が起きたか。** マップ上の勢力マーカーの位置を CSV から取り込む仕組みを作りました。
取り込むと `localStorage` に保存されます。私の環境では完璧に見えていました。

**他の端末で開くと、最大900px以上ずれていました。**

**なぜ素通りしたか。** 取り込み結果を**同梱のシード（初期値）に焼き込むのを忘れていた**からです。
私のPCには `localStorage` の上書きがあるので正しく見える。
初回起動の端末は緯度経度の近似計算にフォールバックし、地図が絵地図なので大きくずれる。

**「自分の環境では動く」の最悪の形**です。しかも例外は一切出ません。

**どう止めたか。** 検査で**`localStorage` を空にしてから**突き合わせるようにしました
（`scripts/verify-force-list.mjs`）。

```js
// 保存済みの状態を必ず消してから開く。これを忘れると自分の環境だけ通る検査になる
await context.clearCookies();
await page.addInitScript(() => { try { localStorage.clear(); } catch {} });
```

**永続化を持つ機能の検査は、必ず「まっさらな状態」から始める。**
これは1行で書けるのに、書いていないと検査の意味が消えます。

## 6. 名前による突き合わせ — 改称した日に静かに切れる

**何が起きたか。** マップ上のマーカーと、勢力データの対応を**名前の一致**で取っていました。
「軒猿」を「軒猿衆」に改称した日、対応が切れました。

例外は出ません。**マーカーは表示され続けます。**ただ、押しても情報が出ないだけです。

**どう止めたか。** 対応をすべて**ID照合**に変えました。
`<勢力ID>_marker` のような命名規約を決めて、名前は表示専用にしました。

**表示用の文字列を、識別子として使わない。**
当たり前に見えますが、最初に書くときは名前が一意なので、つい名前で引いてしまいます。
そして**改称は必ず起きます。**

## 最後に: 検査が本当に効いているかを確かめる（故障注入）

ここまで検査を書いてきて、**自分が書いた検査が素通りしていたこと**が3回ありました。

確かめ方は簡単です。**わざと壊して、検査が落ちるか見る。**

```bash
# 例: ヒステリシスの閾値を1つに潰して、検査が落ちるか確かめる
sed -i 's/pinchUp: 0.58/pinchUp: 0.42/' assets/js/gesture-pointer.js
node scripts/verify-gesture-pointer.mjs   # 落ちなければ、その検査は無意味
git checkout assets/js/gesture-pointer.js
```

これで実際に見つかったすり抜けを3つ挙げます。

**すり抜け1: 検査の並びが「違いの出る場所」を通っていなかった。**
押下判定の閾値を上下2つ持つ（ヒステリシス）実装を検査していたのですが、
**閾値の"外"で往復させる並び**にしていたため、閾値を1つに潰しても同じ結果になりました。
**「閾値の"間"で往復させる」並びに直して、初めて落ちるようになりました。**

**すり抜け2: 「その文字列が在るか」だけを見ていた。**
`source.stop()` が後片付けに書かれているかを検査していたのですが、
同じ文字列が中断時の分岐にもあるので、**後片付けから消しても通りました。**
後片付けの中身だけを切り出して見る形に直して、初めて落ちました。

**すり抜け3: 純粋関数だけを叩いていた。**
座標変換の関数を直接呼んで正しさを確かめていたので、
**まとめ役がその関数に渡す引数を壊す改変**が素通りしました。
「関数は正しいのに動かない」を見逃す典型です。実際に動く経路を通す形に直しました。

**そして故障注入をやるときの注意が1つ。**
**対象の検査だけを走らせること。**私は最初、常に落ちる別件の検査を一緒に走らせてしまい、
3件のすり抜けが「落ちた」の中に埋もれました。
**ノイズが混ざると、故障注入は「すり抜けを見逃す道具」になります。**

## まとめ

- **AIに書かせる開発では、目視レビューは構造的に機能しない。**
  変更速度が人間の確認速度を超えるうえ、AIは「それらしいコード」を書くのが上手い
- **無言で壊れるバグは、結果を実測しないと捕まらない。**
  「関数が呼ばれたか」ではなく「絵が出たか」「音が鳴ったか」を測る
- **エラーを握り潰す実装を書いたら、握り潰した先を見る検査を同時に書く**
- **永続化を持つ機能は、まっさらな状態から検査する。**
  「自分の環境では動く」は、検査を書いても消えない
- **書いた検査は、わざと壊して落ちることを確かめる。**
  落ちない検査は、書いていないのと同じ

検査スクリプトは全部公開リポジトリに置いてあります。
`scripts/verify-*.mjs` を覗いて、使えそうなものは持っていってください。
