「AIエージェントに役割を与えて分業させる」という話は、もう飽きるほど読んだと思います。
企画エージェント、実装エージェント、レビューエージェント。図にすると綺麗に流れます。

**それを実際に1年動かすと、綺麗な図のとおりには動きません。**

私は個人のポートフォリオサイトを Claude Code で開発していて、そこに22体<!--fact:agents-->の
エージェントを定義しています。ブラウザゲームを37本<!--fact:games-->公開し、
検査スクリプトを22本<!--fact:verifiers-->書き、意思決定ログを34本<!--fact:adrs-->積みました。
全部ひとりです。使っているのは Claude Code の定額プランだけで、追加のAPI課金はゼロ円です。

その過程で、エージェント構成を何度も組み替えました。組み替えた理由はいつも同じで、
**「役割の分け方」ではなく「品質ゲートの置き方」を間違えていたから**でした。

## この記事で分かること

- 22体のエージェントが実際にどう繋がっているか（依存関係の全体図）
- 品質ゲートを**直列に置くか並列に置くか**の判断基準と、間違えたときに何が起きるか
- エージェントが増えたときに必ず起きる2つの病気（**孤立**と**重複**）と、その機械的な治し方
- サブエージェントがセッション上限で落ちたときに、作業を失わない受け渡し方
- エージェントに財布を持たせないための予算ガード（PreToolUse hook）

## 先に結論

**エージェントの数は問題ではありません。ゲートの配置が問題です。**

私が最初に作った構成は、企画 → 実装 → レビューの直列でした。動きませんでした。
レビューエージェントが「著作権」「脆弱性」「翻訳漏れ」「実際に起動するか」「仕様との一致」を
全部ひとりで見ていたからです。指摘は毎回20件出て、そのうち本当に直すべきものが3件。
残りは的外れで、直すと別の場所が壊れました。

いま動いている構成は、レビューを**5つに割り、3つを並列・2つを直列**に置いています。

```
[Planner] 仕様
   ├→ [Graphic-Designer] 画像   ┐
   ├→ [Music-Generator]  音     ├→ [Code-Generator] 実装
   └────────────────────────────┘
        ↓
   ┌──── 並列（互いに干渉しない検査）────┐
   │ [Legal-Checker] [Security] [i18n]  │
   └────────────────────────────────────┘
        ↓ 3つとも通過して初めて
   [Dynamic-Tester]  ← 実際にブラウザで起動する（直列）
        ↓ PASS して初めて
   [Evaluator]       ← 仕様と突き合わせて100点満点で採点（直列）
        ↓ 合格
   [Release] → [Marketer]
```

**並列にしたものと直列にしたものの違いは、「他の指摘を前提にするかどうか」です。**
著作権・脆弱性・翻訳漏れは、互いの結果を知らなくても判定できます。だから同時に走らせて時間を潰す。
一方「実際に起動するか」は、上の3つの修正が入った後のコードでないと意味がありません。
採点はさらにその後です。**壊れているコードを採点しても、点数はただのノイズです。**

ここまでが設計の骨格で、ここから先は「そう決めるまでに何を壊したか」の話になります。
実際に踏んだ失敗と、その都度どんな仕組みを足して再発を止めたかを、
コードと検査スクリプトごと全部出します。

## 1. 品質ゲートを直列に並べて失敗した話

最初、私は品質ゲートを全部直列にしていました。理由は単純で、その方が図が綺麗だからです。

```
Legal-Checker → Security → i18n → Dynamic-Tester → Evaluator
```

これで実際に起きたのは、**1周が終わらない**という現象でした。

Legal-Checker が「この画像のライセンス表記が無い」と指摘する。直す。
Security が「その修正で入れた `innerHTML` が XSS になる」と指摘する。直す。
i18n が「その修正で足した英語文が抜けている」と指摘する。直す。
そこまでで1周し、Dynamic-Tester でやっと「起動すらしない」ことが分かる。

**直列にすると、最後のゲートに届くまでに前段を3周する必要が出ます。**
しかも前段の指摘は互いに独立なので、順番に並べる意味が最初から無かった。

並列に変えてからは、3つの指摘がまとめて1回で返るようになりました。
Code-Generator は3つの指摘を一度に見て、互いに衝突しない直し方を選べます。

**判断基準はこうです。**

| ゲート | 他ゲートの結果に依存するか | 配置 |
|---|---|---|
| 著作権チェック | しない（素材の出所を見るだけ） | 並列 |
| 脆弱性チェック | しない（静的解析） | 並列 |
| 日英表記チェック | しない（文言の対応を見るだけ） | 並列 |
| 実際に起動するか | **する**（上の修正後のコードで動くか） | 直列（後） |
| 仕様との一致・採点 | **する**（動くものにしか点は付かない） | 直列（最後） |

そして重要なのは、**直列側のゲートには「前段が終わるまで進ませない」という強制を書くこと**です。
私の定義では Security エージェントに次の一文を入れています。

> CRITICALが1件でも残る場合はDynamic-Testerへ進ませない（Code-Generatorへ差し戻す）

これを書かないと、エージェントは「まあ動くだろう」と判断して先へ進みます。
そして Evaluator の段階で「セキュリティ即不合格」となり、**手戻りが最大になります。**
落とすなら早く落とす。これはCIの原則とまったく同じです。

## 2. エージェントが増えると必ずかかる2つの病気

エージェントは足すのが簡単です。だから増えます。増えると2つの病気が出ます。

### 病気A: 孤立

**定義ファイルは存在するのに、どのフローからも呼ばれないエージェント。**

私は一度、7体が孤立していました。`.claude/agents/` に定義があり、説明文も立派で、
しかし CLAUDE.md のフロー図のどこにも登場しない。誰も起動しない。
存在することを忘れて、同じ役割のエージェントをもう1体作ったこともあります。

これは目視では絶対に見つかりません。定義ファイルは22個あり、フロー図は長いからです。

### 病気B: 重複

**役割が被った2体。** 私の場合、`spec-agent` と `planner`、`debug-agent` と `evaluator` が
それぞれ被っていました。どちらを呼ぶべきか毎回迷い、迷った結果、日によって違う方を呼び、
成果物の置き場所が2つに割れました。

### 治し方: フロー図との一致を機械検査する

この2つは、**「定義ファイルの一覧」と「フロー図に出てくる名前の一覧」を突き合わせるだけ**で
機械検出できます。私は `.claude/skills/self-improve/harness-lint.sh` にこの検査を入れました。

やっていることは単純で、

1. `.claude/agents/*.md` からエージェント名の集合Aを作る
2. CLAUDE.md の「フロー概要」節から `[名前]` の形で登場する集合Bを作る
3. **A − B が空でなければ孤立**（定義があるのに呼ばれない）
4. **B − A が空でなければ幽霊**（フロー図にあるのに定義が無い）

この20行程度の検査を入れた日に、孤立7体が一度に見つかりました。
**「CLAUDE.md に書いてあるから守られている」は成立しません。**
書いてあることと実態が一致しているかを確かめる手段が無ければ、誰も気づかないまま乖離します。

私はこれを一般則として持つようになりました。

> **方針は、それが守られているかを検査できる形で書く。**
> 検査できない方針は、書いた日から腐り始める。

## 3. サブエージェントが落ちたときに作業を失わない

長い実装をサブエージェントに投げると、セッション上限で途中停止することがあります。

このとき私が最初にやった判断が間違いでした。**「停止した＝作業が消えた」と決めつけて、
最初からやり直させた**のです。実際には、**成果物ファイルはディスクに残っていました。**

エージェントは Write でファイルを書きながら進みます。停止したのは会話であって、
書き終えたファイルは消えません。だから正しい手順は、

1. まず `git status` でファイルの実体を確認する
2. 残っている分を活かして、**残作業（テスト・修正）をメイン側が引き継ぐ**
3. 上限リスクが高い局面では、後続の品質ゲートを**エージェント追加起動せずインライン実行**に切り替える

私はこれをそのまま Code-Generator の定義に書き込みました。

> **エージェント停止時の引き継ぎ**: サブエージェントがセッション上限等で停止しても成果物ファイルは
> ディスクに残っていることが多い。「停止＝作業消失」と即断せず、まずファイル実体を確認して
> メイン側が残作業を引き継ぐ。

あわせて、**大きい実装は最初から分割して並行させる**ようにしました。
分割単位はファイル単位かページのセクション単位で、各エージェントに担当範囲を宣言させてから着手させます。
1体に大きい仕事を投げて上限で落ちるより、3体に分けた方が速く、落ちても被害が1/3で済みます。

## 4. エージェントに財布を持たせない

これは事故る前に手を打った数少ない例です。

エージェントは、コストの概念を持ちません。画像生成APIを呼べば絵が出ると知っていれば呼びます。
呼んだ後に「有料でした」と分かります。**個人開発でこれは怖い。**

私は `accounting-agent` という経理エージェントを1体立てて、
実行を止める仕組みは **PreToolUse hook**（`.claude/hooks/accounting-guard.sh`）に持たせました。

**ここが設計の要点です。エージェントに「気をつけて」と書くだけでは止まりません。**
判断はエージェント、強制はhook。役割を分けます。

hook がやることは3つです。

- 課金が発生し得る操作を**実行前に**検知する（対象ツール・コマンドのパターン照合）
- 検知したら承認を要求する（`ask`）
- 月次累計が予算上限を超える見込みなら**ブロックする**（`deny`）

上限は月¥5,000に置いてありますが、これは安全装置であって目標ではありません。
大前提は「有料APIキーを使わない・従量課金サービスを使わない」で、実績は**課金ゼロ**です。
台帳は `accounting/` にMarkdownで置いて、締めは月次のスキルで回しています。

**hookとエージェント定義がずれると、この仕組みは黙って無効になります。**
hook側の照合パターンと、設定ファイル側のツール指定は別々の場所にあるからです。
私は一度これがずれて、ガードが素通りしている状態に2週間気づきませんでした。
いまは harness-lint がこの2箇所の一致も検査しています。

## 5. 22体の全体一覧（何を持たせて、何を持たせないか）

最後に、実際の構成を用途別に置いておきます。**分け方の原則は「入力と出力が違うものは分ける、
判断基準が違うものは分ける、それ以外は分けない」**です。

| 分類 | エージェント | 持たせた責務 | 持たせなかったもの |
|---|---|---|---|
| 横断 | PMO | 進捗・リスク・KPIの一元管理 | 実装 |
| 横断 | Accounting | 課金リスクの監視・予算上限 | 実行の強制（hookが持つ） |
| 上流 | Researcher | 市場調査**専管** | 要件定義 |
| 上流 | Planner | 要件〜詳細設計・仕様書保存 | 市場調査（Researcherの専管） |
| 制作 | Graphic-Designer / Music-Generator | 画像 / 音の制作 | 実装への組み込み |
| 制作 | Code-Generator | 実装のみ | 自己採点 |
| ゲート | Legal-Checker / Security / i18n / Asset-Guardian | 著作権 / 脆弱性 / 日英 / アセット方針（**並列**） | 互いの領域 |
| ゲート | Dynamic-Tester | 実ブラウザ起動（**直列**） | 採点 |
| ゲート | Evaluator | 採点・単独診断 | 修正そのもの |
| 出口 | Release / Marketer | リリース / 宣伝 | 品質判断 |
| 公開後 | Optimizer / Refactoring / Game-Balance / Achievement | 性能 / 構造 / 難易度 / やり込み | 互いの領域 |
| 常設 | Triage | 症状の再現・層の切り分け | 修正そのもの（Edit を持たない） |
| 常設 | Verifier | 無言バグを機械検査へ昇格 | 実装（検査を緑にするのは実装側） |
| 独立 | English-Teacher | 英語学習支援 | パイプラインとの接続 |

**Researcher と Planner を分けた理由**が分かりやすい例です。
最初は Planner に「必要なら市場調査もする」と書いていました。すると Planner は、
調査した内容を要件に混ぜて出してきます。**調査結果と要件の区別がつかなくなり、
「これは調べた事実か、あなたの提案か」を毎回聞き直すことになりました。**

だから調査は完全に切り離し、Planner の定義には
「市場調査はResearcherの専管。Planner自身は市場調査を行わない」と明記しました。
**エージェントを分ける本当の理由は、作業量ではなく、出力の性質を混ぜないためです。**

## まとめ — 明日から効く3つ

1. **ゲートは「他の結果に依存するか」で並列/直列を決める。**
   依存しないものを直列に並べると、周回数が指摘の数だけ増えます
2. **方針は、守られているかを検査できる形で書く。**
   定義ファイルとフロー図の突き合わせは20行で書けて、孤立7体を一度に見つけました
3. **判断はエージェント、強制はhook。**
   「気をつけて」と書いた方針は守られません。実行前に止める層を別に持つこと

この構成のもとになった設定ファイル群（`CLAUDE.md`、`.claude/agents/`、`.claude/hooks/`、
`.claude/skills/`）は、すべて公開リポジトリに置いてあります。
そのまま持っていって、自分のプロジェクトの語彙に置き換えて使ってください。
